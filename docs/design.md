# 설계 배경과 경계

2026-10-10에 [solve-issue-team의 고정 버전](https://github.com/PennyBlack2008/solve-issue-team/tree/94cd9e82c37e3c9fbba55c6567c4ec1057a54bbe)을 확인했습니다. README, commands/solve-issue-team.md, implementer, test-writer, self-reviewer, qa-runner, regression-investigator 역할 정의를 참고했습니다.

| 원본 접근 | 여기서의 선택 | 이유 |
|---|---|---|
| 6개 승인 게이트 | 미결정 방향 + 외부 실행 경계 | 비개발자의 불필요한 대기 줄이기 |
| 계획 대비 diff 검토 | 완료 기준 R1…과 산출물 대조 | 분야와 무관하게 범위 유지 |
| 구현·리뷰·QA 분리 | 제작·비평·증거 검증 책임 분리 | 미적 판단과 실제 확인 구분 |
| 감산 리뷰 | 반복·장식·상충 지시 삭제 | 검토 때문에 결과가 비대해지는 것 방지 |
| 회귀 조사 | 자동 수정 최대 2회, 같은 결함 연속 2회 중단 | 무한 반복 대신 접근 재검토 |
| 파일로 상태 기록 | 복사 가능한 이어하기 카드 | 별도 저장 도구 없는 채팅 지원 |
| 별도 컨텍스트 에이전트 | 단일 AI의 순차 역할 | 실제 독립성에 대한 허위 약속 방지 |

원본의 파일을 복제하지 않고 위 설계 아이디어를 일반 작업에 맞게 새로 작성했습니다. 확인 시 원본 트리에 LICENSE 파일은 없었습니다. 새 저장소의 MIT 라이선스는 원본에 대한 재라이선스를 의미하지 않습니다.

## 프롬프트 구조

정체성 → 절차 → 역할 계약 → 품질 → 증거 → 상태 → 필요한 전문 기준 → 짧은 행동 예시 순서입니다. 단일 배포 파일에 모든 규칙을 포함해 링크를 읽거나 추가 모듈을 설치할 필요가 없습니다. 전문 기준은 해당 작업에만 적용합니다.

명확한 지시, 구분된 섹션, 입력과 기대 응답 예시의 사용은 [OpenAI 공식 Prompt engineering 문서](https://developers.openai.com/api/docs/guides/prompt-engineering)를 참고했습니다(확인: 2026-10-10). 이 문서가 본 키트의 효과나 다른 서비스에서의 성능을 보증하는 것은 아닙니다.

## 의도적인 제약

- 역할 전환은 권한 격리나 독립 검토가 아니다.
- 프롬프트에 적힌 한도는 소프트웨어로 강제되는 실행 제한이 아니다.
- 최신 생성 도구별 파라미터를 고정하지 않는다. 공식 자료나 사용자 설정을 확인하기 전까지 도구 중립 문구를 쓴다.
- 승인된 계획도 사용자가 바꿀 수 있다. 명확한 변경 지시는 새 승인으로 기록한다.
- 검증은 실제 접근 가능한 범위를 넘지 않는다. 구조 검사 통과와 모델 행동 검증은 별개다.

## 확장 방법

새 분야는 `specialists/`에 적용 조건·입력·산출물 계약·검증 범위만 추가하세요. 공통 승인·수정·증거 규칙을 덮어쓰지 마세요. manifest에 등록하고 해당 예제와 실패 사례를 평가 목록에 추가합니다. 큰 도구별 매뉴얼은 마스터 프롬프트를 부풀리지 말고 별도 참고 문서로 두세요.
